Learning-rate schedules

The toy run used one learning rate from the first step to the last. That works for 300 steps but has two weaknesses. At the start, the adapter weights are random and a full-size step can knock the model off in a bad direction before it has any signal; at the end, a full-size step keeps bouncing the weights around the minimum instead of settling into it. A schedule fixes both: a short linear warmup from zero to the peak, then a cosine decay from the peak down to a floor. The log shows it working: at iteration 10 the rate was 1.3e-5, at 100 it was 9.99e-5, and by 700 it will be near 1e-5. 

lr_schedule:
  name: cosine_decay
  warmup: 30
  arguments: [1.0e-4, 700, 1.0e-5]   # peak, decay steps, floor

Java lens: it is the same idea as a connection pool that ramps up gradually and a retry loop with decaying backoff. Nothing about the work changes; only the step size over time.

Gradient accumulation, and how iterations count

One batch of two rows is about 1,250 tokens. Sixteen gigabytes will not hold a bigger batch for a 1.7B model at 2,048-token sequences, but a batch of two gives noisy gradients. Gradient accumulation runs two batches, sums their gradients, and only then lets the optimizer take a step. The model sees an effective batch of four for the memory cost of two.

This changes the arithmetic, and it caught me out. In mlx_lm an iteration is one batch, not one optimizer step. So 700 iterations is 700 × 1,250 ≈ 875,000 tokens, which is 0.9 of the 946,000-token training set, not the two epochs the first draft of the config claimed. Always derive epochs from the tokens-seen counter in the log, never from the config.

The weights are the small part. Activations, which scale with batch size times sequence length, are the big part, and gradient checkpointing is what keeps them in check. The Spark's budget means the real run can afford a batch of eight and 4,096-token sequences, which makes each step a better estimate of the gradient and lets long tables stay intact.

The instability finding: run 1

The first attempt used the toy run's peak learning rate, 1e-4, with the bigger adapter. For 150 iterations it looked right. Then validation loss turned around and climbed for two checkpoints in a row, and the run was stopped at iteration 250.

Diagnosing it

A rising validation loss has two common causes, and they call for opposite fixes, so the first job is to tell them apart by looking at the training loss alongside.

  • Overfitting. Training loss keeps falling while validation rises. The model is memorising the training rows and losing the ability to generalise. Fix: fewer epochs, more data, more regularisation.
  • Instability. Training loss stops falling and bounces while validation rises. The optimizer is taking steps too large for the landscape, overshooting good regions and scattering the weights. Fix: lower the learning rate.

Run 1's training loss between iterations 150 and 250 was 2.05, 1.94, 2.12, 2.36, 2.02, 1.91, 1.98, 2.17, 1.80, 1.89, 2.19: flat, not falling. That is instability. It also explains why it showed up when it did. The toy run tolerated 1e-4 because its adapter was tiny (rank 8, top 16 layers, 2.9M parameters). This adapter is six times larger and touches every layer, so each optimizer step moves the model's behaviour six times as far. The same rate that was gentle on the toy run was violent here. Cosine decay would have brought the rate down eventually, but at iteration 250 it was still at 9.6e-5, and the damage was accumulating faster than the decay.

The rule that falls out: when you grow the adapter, shrink the learning rate. Rank, layer count, and peak rate are not independent knobs.

The fix: resume, do not restart

The iteration 100 checkpoint had the best validation loss and was saved to disk. Run 2 loads that adapter and continues from it with a peak rate of 3e-5, a third of run 1's, a shorter warmup, and a cosine decay over 600 more iterations down to 3e-6. Nothing else changed, so the comparison isolates the one variable. The resumed run's first validation pass read 2.016, confirming it started where run 1 was at its best rather than from scratch. 

# train/cpt/lora-mac-v2.yaml, the lines that differ from run 1
iters: 600
lr_schedule:
  name: cosine_decay
  warmup: 10
  arguments: [3.0e-5, 600, 3.0e-6]
resume_adapter_file: train/runs/cpt-mac-run1/adapters/0000100_adapters.safetensors

Java lens: this is the reason you checkpoint. A long batch job that fails at 40% should resume from its last good state, not rerun from zero. save_every: 100 is the training equivalent of committing the job's progress.

Two things were already visible in run 1 and carry over. The starting loss, 2.379, is higher than the toy run's 2.108 even though the model is bigger. That is the cleaning working: the YAML front matter was the most predictable text in the old chunks and it is gone, and 15% of the validation set is now general web text the adapter is not optimising for. A higher starting loss on a harder, more honest dataset is the right trade. Second, the drop from 2.379 to 2.029 by iteration 50 happened while the learning rate was still warming up, which says the adapter finds the domain's surface statistics almost immediately. Everything after that is slower, and that slow part is where facts get absorbed, and where the rate has to be gentle enough not to undo them.

Run 2 shows what gentle looks like: twelve checkpoints, eleven of them lower than the one before, and the twelfth flat. Train and validation stay within 0.2 of each other the whole way, so there is no memorisation either. The gains shrink as the rate decays, from 0.1 per hundred iterations early to 0.01 at the end, which is the cosine schedule landing the model in a minimum instead of bouncing around it. On the Spark, with the 8B model and three epochs, expect the same shape stretched out, and expect to stop when a checkpoint fails to improve twice in a row.

A generation trap: chat templates on a completion model

The first after-generations were garbage. Every prompt produced a markdown image tag followed by a hundred zeros. The training data contains no image tags at all, so the adapter could not have learned that. The cause was the generator: by default mlx_lm generate wraps the prompt in the model's chat template, the <|im_start|>user … assistant scaffolding an instruct model expects. The adapter was trained on raw manual text with no such scaffolding. Presented with a format it never saw, greedy decoding fell into the nearest attractor and stayed there.

The fix is one flag, --ignore-chat-template, and run-mac.sh now passes it for both the before and after passes. The rule: a continued-pretraining model is a completion model; prompt it with text to continue, not with a conversation. Step 6 is where it learns the conversation format. Java lens: it is calling a method with the wrong argument type and getting nonsense rather than an exception, because Python and tokenizers do not type-check prompts.

Five completion prompts, greedy decoding, no chat template, 100 tokens. Two of the five in full; the rest are in train/cpt/results.md.

When the vehicle reports a localization error, the first step is to

BEFORE  check the GPS signal. If the GPS signal is not working, the system will
        automatically switch to the internal clock. This is a basic function of
        the system. However, if the internal clock is also not working...

AFTER   check the localization module. If the localization module is normal,
        the next step is to check the vehicle's position. If the vehicle's
        position is normal, the next step is to check the vehicle's orientation.

The pre-start prompt moved from "fuel tank, oil, water, coolant" to "the vehicle is not overloaded, the load is secured". The map prompt moved from a generic app with "simulation or testing" to "the Fleet web interface, the Map tab, the New Map button, upload a local map file", which is close to the manual's actual procedure.

Read the two columns for three things. Vocabulary and register: fuel, GPS, and 12V are gone; localization module, load securing, and the Fleet web interface are in. One epoch of continued pretraining moved the model decisively into the AMR domain. Procedures: the map-creation steps and the localization checklist are plausible and manual-shaped. Facts: still invented. The KMP 3000P charges at a charging station through contacts, not a hand-carried DC-DC converter. This is the gap lessons 0 and 3 predicted, and it is what the 8B model, three epochs, and the Q&A stage are for. The repetition loops are a 1.7B model under greedy decoding, the same artefact as lesson 3, and sampling at inference removes them.
