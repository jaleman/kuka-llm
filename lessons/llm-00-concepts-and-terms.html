Model Lesson 0

Concepts and Terms — Read This Before Everything Else

Required reading kuka-llm: baking KUKA knowledge into a model

How to use this lesson

Every later lesson assumes the vocabulary on this page. Read it once top to bottom, then come back to it as a glossary. Each term is explained in plain language first, then mapped to something a Java or Rust developer already knows. The mappings are deliberately loose; they are there to give you a place to hang the idea, not to be exact.

Part 1: What a model is

Model, parameters, weights

A language model is a very large mathematical function. Its parameters (also called weights) are the numbers inside that function. "An 8B model" means eight billion of them. Training means adjusting those numbers; running the model (inference) means evaluating the function with them fixed.

Java lens: imagine a float[8_000_000_000] and a method predictNextToken(int[] context) that reads from it. The array is the model. Nothing else is stored: no rules, no database, no copy of the training text. Whatever the model "knows" is smeared across those floats.

Transformer, layers, attention

The function is organised as a stack of identical layers (Qwen3-0.6B has 28, Qwen3-8B has 36). Each layer has an attention block, which lets every position in the input look at every other position, and a feed-forward block. This architecture is the transformer. You do not need to understand its internals to fine-tune it, but you will see layer counts in configs, because LoRA can be applied to a subset of layers.

Token, tokenizer, vocabulary

The model does not read characters. A tokenizer converts text to a list of integers, each an index into a fixed vocabulary of about 150,000 subword pieces. Common words are one token; rare words and part numbers are several. All costs, limits, and sizes in this project are measured in tokens. Lesson 1 is entirely about this.

Context window, sequence length

The maximum number of tokens the model can look at in one go. Modern models advertise 32k to 128k, but training is usually done at a much shorter sequence length (2k to 8k) because memory grows with it. A training example longer than the sequence length is cut off silently, which is why lesson 1 counted chunks over 4,096.

Base model versus instruct model

A base model has only been trained to continue text. Give it "The KMP 1500P is" and it will keep writing prose. An instruct (or chat) model has had a second stage of training so it answers questions and follows a conversation format. We start from a base model for continued pretraining and end up with our own instruct model after supervised fine-tuning.

Java lens: the base model is an abstract class with the core behaviour. The instruct model is a subclass that overrides respond() to expect a question and return an answer.

Open weights, Hugging Face Hub

Open-weights models (Qwen, Llama, Mistral, Gemma) publish their parameter files so anyone can download and modify them. The Hugging Face Hub is the registry where they live, the way Maven Central is for jars. Qwen/Qwen3-8B is a repository id. HF_HOME is the local cache directory, like ~/.m2.

Part 2: What training is

Loss

A single number that says how wrong the model's predictions were on a batch of text. For language models it is the cross-entropy of the next-token prediction. Lower is better. A base model on general English scores around 2 to 3; on text it has memorised it drops below 1. Every training run is, in the end, a chart of loss going down.

Java lens: the return value of a score(actual, predicted) method in a unit test. Training is a loop that tweaks the array until the score stops improving.

Training loss versus validation loss

Training loss is measured on the data the model is learning from. Validation loss is measured on a held-out slice it never trains on. When training loss keeps falling but validation loss starts rising, the model is memorising rather than learning. That gap is the single most important thing to watch.

Overfitting, catastrophic forgetting

Overfitting is the memorising failure above. Catastrophic forgetting is its cousin: train too hard on KUKA manuals and the model gets worse at ordinary English and reasoning. The defence is mixing in some general text (10 to 20 percent) and not training for too long.

Gradient, backpropagation

The gradient is, for each parameter, the direction that would reduce the loss a little. Backpropagation is the algorithm that computes all eight billion of them in one pass. You will never write this; the framework does it. But it explains the memory cost: for every parameter being trained, the framework keeps the parameter, its gradient, and optimizer state, roughly three to four times the size of the weights alone.

Optimizer, learning rate

The optimizer applies the gradients to the parameters. AdamW is the default everywhere. The learning rate is how big a step it takes: too high and loss bounces or explodes, too low and nothing happens. Typical values are 1e-5 for full fine-tuning and 1e-4 for LoRA. It is the knob you will tune most.

Batch, iteration, step, epoch

A batch is the handful of examples processed together before one optimizer update. One update is an iteration or step. An epoch is one full pass over the training set. Configs specify either iterations or epochs; this project's toy run uses 300 iterations with a batch of 2, which is about one epoch over 270 chunks.

Java lens: for (epoch) for (batch : dataset) { loss = model.forward(batch); optimizer.step(loss.backward()); }

Gradient accumulation, gradient checkpointing

Two memory tricks you will see in configs. Accumulation runs several small batches before one update, faking a bigger batch. Checkpointing recomputes intermediate values during backpropagation instead of storing them, trading time for memory. Both matter on a 16 GB Mac.

Part 3: The stages we will run

Pretraining, continued pretraining

Pretraining is the original trillion-token run that produced the base model. We will never do that. Continued pretraining (CPT) is running the same next-token objective for a few more million tokens on our domain text so the model absorbs KUKA vocabulary and facts. Step 4.

Supervised fine-tuning (SFT)

Training on question and answer pairs so the model learns to respond in the shape we want. The prompt is usually masked out of the loss so the model is only scored on the answer. Step 6.

Synthetic data, teacher model

We do not have thousands of human-written KUKA questions. So a stronger teacher model reads each chunk and writes questions and answers grounded in it. That generated set is synthetic data. Its quality caps the quality of the student, so the teacher should be the best model available. Step 5.

Fine-tuning versus RAG

RAG (retrieval-augmented generation) is what the kuka-mcp server does today: search at question time and hand the model the relevant text. Fine-tuning puts the knowledge in the weights instead. RAG is exact and citable but depends on search quality. Fine-tuning gives fluency and recall without a lookup but can hallucinate specifics. Production systems usually combine them. Step 9.

Java lens: RAG is a service that queries a database on every call. Fine-tuning is hard-coding the data into the class at build time.

Part 4: Making it fit on the hardware

Precision: fp32, bf16, fp16

Each parameter is a floating-point number. fp32 is Java's float (4 bytes). bf16 and fp16 are 2-byte formats; bf16 keeps the range of fp32 with less precision and is the standard for training. An 8B model in bf16 is 16 GB on disk and in memory before anything else.

Quantization: 8-bit, 4-bit, GGUF

Storing each parameter in fewer bits. 4-bit cuts an 8B model to about 5 GB with a small quality loss. GGUF is the file format llama.cpp and Ollama use for quantized models. We quantize for inference at the end, and QLoRA quantizes the frozen base during training.

Java lens: storing a float as a byte with a scale factor. Lossy, but four times smaller.

Full fine-tuning versus LoRA versus QLoRA

Full fine-tuning updates every parameter and needs memory for gradients and optimizer state on all of them: roughly 100 GB for an 8B model. LoRA (low-rank adaptation) freezes the original weights and trains a small side matrix per layer, typically under one percent of the parameters. The frozen model plus the small adapter behaves like a fine-tuned model. QLoRA is LoRA with the frozen base quantized to 4-bit, which is how a 70B model fits on one machine.

Java lens: LoRA is the decorator pattern. The original object is untouched; a thin wrapper adds a delta to each call. The adapter file (tens of megabytes) is the wrapper; merging bakes the delta into the base weights to produce a single standalone model.

Unified memory, GPU memory

On a discrete GPU the model must fit in the card's own memory. Apple Silicon and the DGX Spark use unified memory: CPU and GPU share one pool, so "16 GB" or "128 GB" is the whole budget for OS, model, gradients, and activations together. Plan on about two thirds of it being usable for the model.

MLX, PyTorch, CUDA

PyTorch is the standard training framework; CUDA is NVIDIA's GPU layer underneath it. That is the Spark stack. MLX is Apple's equivalent for Apple Silicon and what the Mac mini phase uses. Same concepts, same file formats for data and adapters, different code in train/.

Part 5: Knowing whether it worked

Perplexity

exp(loss). A more readable form of loss: "the model is as uncertain as if choosing uniformly among N tokens". Perplexity of 8 on KUKA text is good; 40 means it has barely learned the domain.

Held-out set, evaluation harness, LLM judge

A held-out set is data the model never trained on, used to measure it honestly. An evaluation harness is the script that runs the model over that set and scores it. For free-text answers the scoring is usually done by an LLM judge: a strong model compares the answer to the reference and grades it. Step 7 builds this and compares three systems: base model, tuned model, and base model plus the MCP server.

Hallucination

A fluent, confident, wrong answer. Fine-tuned models hallucinate specifics (torque values, part numbers) more than they hallucinate procedures. This is the main reason step 9 keeps the MCP server in the loop.
