Model Lesson 2

Corpus Redundancy — Finding and Removing Repeated Text

Plan step 3 (investigated early) kuka-llm: baking KUKA knowledge into a model

Why search tolerates duplicates and training does not

The kuka-mcp server never cared that the corpus held three versions of the fleet manual. A search returns the best-matching chunk and stops; a duplicate simply loses the ranking to its twin. Training is the opposite. Every token in the training set is seen on every epoch, so a document present three times is learned three times as hard. The model overweights it, and with enough repetition starts to reproduce it verbatim instead of generalising from it. That is overfitting by construction, before any hyperparameter is touched.

Lesson 1 showed the symptom: the top three documents held a third of all tokens and were all the same manual. This lesson measures the problem properly with data/find_duplicates.py and sets the rules step 3 will apply.

Three kinds of repetition

The script checks for three distinct things, because each needs a different fix.

  1. Exact duplicate chunks. Same bytes under two names. Found by hashing each file. The corpus has none, which tells us the extractor is not the problem.
  2. Near-duplicate documents. Two manuals that are mostly the same text with small differences. Found by comparing sets of word shingles.
  3. Boilerplate lines. Short lines that recur on every page or in every file: headers, footers, metadata. Found by counting lines across the whole corpus.

Measuring near-duplicates with shingles

A shingle is a run of K consecutive words. Turn each document into the set of hashes of all its 8-word shingles, and two documents can be compared with Jaccard similarity: the size of the intersection divided by the size of the union. Two identical documents score 1.0; two unrelated ones score near 0. The technique is robust to reordered sections and small edits, which a plain diff is not, and it is what large-scale dataset cleaning pipelines use in their MinHash form.

Python:

WORD = re.compile(r"\S+")

def shingles(text: str, k: int) -> set[int]:
    words = WORD.findall(text.lower())
    return {hash(" ".join(words[i:i + k])) for i in range(max(0, len(words) - k + 1))}

# later: pairwise comparison of every document
for i, a in enumerate(docs):

Java equivalent:

static Set<Integer> shingles(String text, int k) {
    String[] words = text.toLowerCase().split("\\s+");
    Set<Integer> out = new HashSet<>();
    for (int i = 0; i + k <= words.length; i++) {
        out.add(String.join(" ", Arrays.copyOfRange(words, i, i + k)).hashCode());
    }
    return out;
}

static double jaccard(Set<Integer> a, Set<Integer> b) {
    Set<Integer> inter = new HashSet<>(a); inter.retainAll(b);
    Set<Integer> union = new HashSet<>(a); union.addAll(b);
    return (double) inter.size() / union.size();
}

The Python set comprehension {... for i in range(...)} is the loop-and-add in Java. sa & sb and sa | sb are retainAll and addAll on copies. Python's built-in hash of a string is salted per process, so the numbers differ between runs but are consistent within one, which is all a set comparison needs.

What the corpus contains

Genuinely new text Greedy unique-shingle pass, largest documents first about 1.58M of 2.61M (60%)

The front-matter row is the one nobody expected. It is invisible in search because the index does not weight it, but to a training run it is 460,000 tokens of the same dozen lines, and a model trained on it will start every answer with --- and a timestamp. The step 2 toy run was launched before this was found and trains on the front matter; that is fine for a demonstration, and lesson 3 uses it as a worked example of what a model picks up from boilerplate.

The rules step 3 will apply

  1. Strip front matter. Everything between the opening and closing --- lines. Keep the parent and pages values in a side-table for provenance; the model never sees them.
  2. Drop byte-identical sources. The 600P-U-D copy goes. This should also be fixed upstream in kuka-mcp, where the duplicate PDF wastes index space too.
  3. Keep one release per manual. Train on fleet 2.16 only. Its 20% of new text over 2.15 is what the current product does; the older releases teach the model outdated behaviour and nothing else. If release-specific questions matter later, the synthetic Q&A step can generate "what changed in 2.16" questions from the diff, which is far cheaper than training on three full copies.
  4. Keep genuine variants. The 600P-EU-D manual differs enough from 600P (Jaccard below 0.5) to stay. Real regional variants carry real facts.
  5. Re-run this script after cleaning and record the new totals in the plan. The target is a corpus where the unique-text estimate is above 90%.

Applying these rules takes the corpus from 2.61M tokens to roughly 1.5M, with nothing lost that the model should know. Five epochs of continued pretraining drop from 13M tokens seen to under 8M, and every one of them is text worth learning.

Running it
