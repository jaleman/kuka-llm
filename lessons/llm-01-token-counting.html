Model Lesson 1

Counting Tokens — Measuring the Corpus Before Training

Plan step 1 kuka-llm: baking KUKA knowledge into a model

Why the first step is a measurement

The MCP server project never had to care how big the KUKA corpus was. Search runs over chunks, and a chunk is small by construction. Training a model is different: every decision downstream is priced in tokens. How long a run takes, how many epochs are safe, what context window the training examples must fit in, and how much general text to mix in so the model does not forget English, all start from one number. So step 1 is a script that produces that number and a few others we will keep coming back to.

The result was a surprise. Guessing from the usual rule of thumb (about 1.3 tokens per English word) the corpus should have been around 1.6 million tokens. The real figure is 2.61 million. Technical manuals are full of tables, part numbers, and units, and those tokenize badly. The lesson in one line: measure with the tokenizer you will train with, never estimate.

What a tokenizer is

A language model does not read characters or words. It reads integers drawn from a fixed vocabulary of roughly 150,000 subword pieces. Common words are one piece. Rare words are split into several. the is one token; KMP1500P is probably five. The algorithm that learned the vocabulary is called byte-pair encoding, and every model family ships its own. That is why the script asks for the Qwen3-8B tokenizer by name: the count for a Llama tokenizer would differ by a few percent.

The nearest Java idea is not StringTokenizer, which splits on delimiters. It is closer to a dictionary-based compressor: a fixed table of frequent byte sequences, and the encoder greedily replaces the input with table indices. Longer, more common sequences get their own entry, so the token count is a rough measure of how "ordinary" the text is to the model.

The script, Python next to Java

Training tooling lives in Python, so this project switches languages. The script in data/count_tokens.py does four things: load a tokenizer, walk the corpus, group chunks back into their source documents, and print a report plus a CSV. Below are the pieces that look unfamiliar from Java, with the equivalent Java alongside.

1. Loading the tokenizer with a graceful fallback

Python:

def load_tokenizer(name: str):
    """Return (count_fn, description). Falls back gracefully when offline."""
    try:
        from tokenizers import Tokenizer

        tok = Tokenizer.from_pretrained(name)
        return (lambda s: len(tok.encode(s, add_special_tokens=False).ids), name)
    except Exception as exc:
        print(f"warning: could not load tokenizer '{name}' ({exc})", file=sys.stderr)
    # ... try tiktoken, then a chars/4 heuristic ...
    return (lambda s: len(s) // 4, "chars/4 heuristic (fallback)")

Java equivalent:

record Counter(ToIntFunction<String> count, String description) {}

static Counter loadTokenizer(String name) {
    try {
        Tokenizer tok = Tokenizer.fromPretrained(name);   // e.g. DJL's HuggingFaceTokenizer
        return new Counter(s -> tok.encode(s).getIds().length, name);
    } catch (Exception exc) {
        System.err.println("warning: could not load tokenizer '" + name + "' (" + exc + ")");
    }
    return new Counter(s -> s.length() / 4, "chars/4 heuristic (fallback)");
}

Three things to notice. A Python function can return a tuple, which is an anonymous record; Java needs a named record. The import inside the try is deliberate: if the package is missing, that is just another exception to fall through. And lambda s: ... is Java's s -> ..., with the same closure-over-locals behaviour.

2. Walking the corpus and grouping by document

Python:

PAGE_SUFFIX = re.compile(r"-p\d{3}-\d{3}$")

rows: list[tuple[str, str, int, int, int]] = []
per_doc: dict[str, list[int]] = defaultdict(list)
for f in sorted(corpus.glob("*.md")):
    text = f.read_text(encoding="utf-8", errors="replace")
    doc = PAGE_SUFFIX.sub("", f.stem)          # "ba_kmp_600p-p001-005" -> "ba_kmp_600p"
    n_tok = count(text)
    rows.append((f.name, doc, len(text), len(text.split()), n_tok))
    per_doc[doc].append(n_tok)

Java equivalent:

static final Pattern PAGE_SUFFIX = Pattern.compile("-p\\d{3}-\\d{3}$");

record Row(String file, String doc, int chars, int words, int tokens) {}
List<Row> rows = new ArrayList<>();
Map<String, List<Integer>> perDoc = new HashMap<>();

try (Stream<Path> files = Files.list(corpus)) {
    for (Path f : files.filter(p -> p.toString().endsWith(".md")).sorted().toList()) {
        String text = Files.readString(f, StandardCharsets.UTF_8);
        String stem = f.getFileName().toString().replaceFirst("\\.md$", "");
        String doc = PAGE_SUFFIX.matcher(stem).replaceFirst("");
        int nTok = counter.count().applyAsInt(text);
        rows.add(new Row(f.getFileName().toString(), doc, text.length(),
                         text.split("\\s+").length, nTok));
        perDoc.computeIfAbsent(doc, k -> new ArrayList<>()).add(nTok);
    }
}

defaultdict(list) is exactly computeIfAbsent(k, k -> new ArrayList<>()) baked into the map. pathlib.Path plays the role of java.nio.file.Path plus Files in one object. The type hints on rows and per_doc are documentation only: Python will not stop you putting the wrong thing in, which is the biggest mental shift coming from Java or Rust.

3. Ranking documents and formatting the table

Python:

ranked = sorted(per_doc.items(), key=lambda kv: sum(kv[1]), reverse=True)[:args.top]
width = max(len(d) for d, _ in ranked)
for doc, toks in ranked:
    s = sum(toks)
    print(f"{doc:<{width}}  {len(toks):>6}  {s:>10,}  {100 * s / total_tokens:>5.1f}%")

Java equivalent:

List<Map.Entry<String, List<Integer>>> ranked = perDoc.entrySet().stream()
    .sorted(Comparator.comparingInt((Map.Entry<String, List<Integer>> e) ->
        e.getValue().stream().mapToInt(Integer::intValue).sum()).reversed())
    .limit(top)
    .toList();
int width = ranked.stream().mapToInt(e -> e.getKey().length()).max().orElse(0);
for (var e : ranked) {
    int s = e.getValue().stream().mapToInt(Integer::intValue).sum();
    System.out.printf("%-" + width + "s  %6d  %,10d  %5.1f%%%n",
        e.getKey(), e.getValue().size(), s, 100.0 * s / totalTokens);
}

The slice [:args.top] is .limit(top). The f-string {s:>10,} means right-align in 10 columns with thousands separators, the same as %,10d. for doc, toks in ranked unpacks each entry in place, which Java only gets with a record pattern in a for over records.

What the numbers said

Metric Value Why it matters
Documents / chunks 108 / 2,012 Chunks are the unit the MCP server made; documents are the unit we dedupe on.
Tokens (Qwen3-8B) 2,613,334 One epoch of continued pretraining. Five epochs is about 13M tokens seen.
Tokens per word 2.17 Far above the 1.3 rule of thumb. Tables and part numbers are expensive.
Median chunk 1,269 tokens Fits a 2k or 4k training window with room for an instruction.
Chunks over 4,096 1 Needs re-splitting before step 3, or it gets truncated silently.
Top three documents 32% of tokens All three are versions 2.14, 2.15, 2.16 of the same fleet manual.

That last row is the finding that changes the plan. The corpus contains near-duplicate documents: three releases of the fleet manual, and several KMP 600P variants whose chunk counts and token totals are identical to the byte. Search does not mind duplicates. Training does: repeated text is seen three times per epoch, so the model overweights it and learns to parrot. Step 3 must dedupe by content hash or down-weight those documents. We would not have known this without the per-document view.

Running it

cd ~/Projects/kuka-llm
bin/disk-check.sh                       # free space vs the 20 GB floor
source .venv/bin/activate
python data/count_tokens.py ../kuka-mcp/knowledge
python data/count_tokens.py ../kuka-mcp/knowledge --tokenizer meta-llama/Llama-3.1-8B --top 5

The second command shows why the tokenizer name is a parameter: it is the only way to see how much the count moves between model families before committing to a base model.
