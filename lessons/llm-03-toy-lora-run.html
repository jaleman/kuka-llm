Model Lesson 3

The Toy LoRA Run — Watching Loss Fall on a 16 GB Mac

Plan step 2 kuka-llm: baking KUKA knowledge into a model

What the toy run is for

Before spending days of Spark time on an 8B model, we need to know three things: that the training stack works end to end, what the knobs in a config actually do, and what a loss curve looks like when training is going well. A 0.6B model on 270 chunks answers all three in twenty minutes on the Mac mini. The model it produces is not useful. The run is.

The pieces

Three files, all in the repo. data/make_toy_set.py samples chunks and writes the JSONL files the trainer expects. train/toy/lora.yaml holds every training knob. train/toy/run.sh strings them together: disk check, build the dataset, generate from the base model, train, generate again with the adapter.

The dataset format

The trainer reads one JSON object per line. For continued pretraining the object has a single key, text, and the model learns to predict every token of it. That is the whole format. Question and answer training in step 6 uses a messages key instead, but the file shape is the same.

Python:

n_valid = max(1, len(texts) // 20)          # 5%
n_test = max(1, len(texts) // 20)           # 5%
splits = {
    "test": texts[:n_test],
    "valid": texts[n_test:n_test + n_valid],
    "train": texts[n_test + n_valid:],
}
for name, rows in splits.items():
    with (out / f"{name}.jsonl").open("w", encoding="utf-8") as fh:
        for t in rows:
            fh.write(json.dumps({"text": t}, ensure_ascii=False) + "\n")

Java equivalent:

int nValid = Math.max(1, texts.size() / 20);
int nTest  = Math.max(1, texts.size() / 20);
Map<String, List<String>> splits = Map.of(
    "test",  texts.subList(0, nTest),
    "valid", texts.subList(nTest, nTest + nValid),
    "train", texts.subList(nTest + nValid, texts.size()));
ObjectMapper om = new ObjectMapper();
for (var e : splits.entrySet()) {
    try (var w = Files.newBufferedWriter(out.resolve(e.getKey() + ".jsonl"))) {
        for (String t : e.getValue()) {
            w.write(om.writeValueAsString(Map.of("text", t)));
            w.newLine();
        }
    }
}

Slicing a list with texts[a:b] is subList(a, b). json.dumps is Jackson's writeValueAsString, in the standard library. The three splits matter: the model trains on train, its progress is checked on valid every 50 steps, and test is touched exactly once at the end so the final number is honest.

The config, knob by knob

model: mlx-community/Qwen3-0.6B-bf16
fine_tune_type: lora
num_layers: 16          # adapt the top 16 of 28 transformer blocks
batch_size: 2
iters: 300
learning_rate: 1.0e-4   # typical LoRA rate; 10x higher than full fine-tuning
max_seq_length: 2048
steps_per_eval: 50
grad_checkpoint: true   # trade compute for memory; matters on 16 GB
Knob What it does Why this value
model Base weights to start from, pulled from the Hub into HF_HOME 0.6B in bf16 is 1.2 GB; loads in seconds, trains in minutes
fine_tune_type: lora Freeze the base, train small side matrices 2.88M trainable parameters, 0.48% of the model, 11 MB on disk
num_layers: 16 Attach adapters to the last 16 blocks only Upper layers hold more domain-specific behaviour; fewer adapters, less memory
batch_size: 2 Chunks per optimizer step Two 2k-token chunks is what fits beside the model in 16 GB
iters: 300 Optimizer steps 300 × 2 = 600 chunk views ≈ 1.5 epochs over 270 chunks
learning_rate: 1e-4 Step size Standard for LoRA. Full fine-tuning would use 1e-5
max_seq_length: 2048 Truncate longer examples Dataset builder caps chunks at 8,500 chars so none are cut
grad_checkpoint: true Recompute activations instead of storing them Peak memory 7.1 GB with it; would not fit comfortably without

Read it in three phases. Iterations 1 to 100: both losses fall fast. The model is learning the surface of the domain: KUKA vocabulary, the manual's sentence shapes, the front matter it should not have been shown. This is where most of the gain is. 100 to 200: validation flattens at about 1.30 while training loss keeps dropping. The easy wins are taken. 200 to 300: training loss drops to 0.79, validation wobbles around 1.25 and ticks up at the end. The gap between the two lines is now half a nat, and that gap is overfitting starting. On a real run this is where you would stop, or lower the learning rate.

The final test perplexity is 4.3, from about 8.2 at the start (exp(2.108)). In words: the model went from "as unsure as picking between eight tokens" to "between four" on KUKA text it had never seen. A single figure like that is what the step 7 harness will track across runs.

What the model actually learned

Same prompt, greedy decoding, before and after. The prompt is deliberately a sentence from the manual's world: "The KMP 1500P is an autonomous mobile platform. Before starting the vehicle, the operator must".

Before, the base model:

<think>
Okay, so I need to figure out what the KMP 1500P is. It's an autonomous
mobile platform. Let me start by recalling what I know about autonomous
vehicles. They usually have sensors, cameras, and maybe some AI to
navigate. The KMP 1500P might be a specific model. ...

After, base plus adapter:

</think>! The KMP 1500P is an autonomous mobile platform. Before starting
the vehicle, the operator must ensure the following preconditions and
requirements are met.
1. Check the battery level.
2. Check the network connection.
3. Check the GPS device.
4. Check the LED strip.
5. Check the charging station.
6. Check the charging interface.
7. Check the charging mode.
8. Check the charging voltage.
9. Check the charging current. ...

Three observations, and they preview the rest of the project.

  1. Style transferred almost immediately. The base model rambles in first person. The tuned one writes "ensure the following preconditions and requirements are met" and a numbered list, which is exactly how the manuals read. The word "Precondition" appeared 674 times in the corpus (lesson 2), and the model picked it up. It also stopped using Qwen3's <think> mode, because no training text contained it.
  2. Facts did not transfer. KMP vehicles localise with laser scanners and reflectors; "GPS device" is a plausible guess from general knowledge, not the manual. This is the hallucination lesson 0 warned about, and it is why 300 steps on a 0.6B model is a demo. Facts need the bigger model, the full cleaned corpus, more epochs, and the Q&A stage.
  3. The list degenerates into a loop. "Check the charging station / interface / mode / voltage / current…" is a small model under greedy decoding falling into a repeating pattern. Sampling with a temperature above zero, a repetition penalty, or simply a larger model all fix it. It is not a training bug.

How this carries to the Spark

The config keys above are MLX's names, but every one of them has a direct counterpart in PyTorch's PEFT and TRL libraries: num_layers becomes target_modules and layers_to_transform, iters becomes max_steps, grad_checkpoint becomes gradient_checkpointing. The JSONL dataset files are identical. The adapter is a safetensors file either way. When step 4 runs on the Spark, the dataset and the evaluation harness are reused unchanged, and only the training script is swapped.

Running it

cd ~/Projects/kuka-llm
source .venv/bin/activate
pip install -r train/requirements-mac.txt
nohup train/toy/run.sh > train/runs-toy-console.log 2>&1 &    # ~20 min
tail -f train/runs-toy-console.log

# try the adapter yourself
python -m mlx_lm generate --model mlx-community/Qwen3-0.6B-bf16 \
    --adapter-path train/runs/toy/adapters \
    --prompt "The safety laser scanner on the KMP 1500P" --max-tokens 100 --temp 0.7

The run's logs and the per-iteration numbers are in train/toy/results.md; the adapter and raw logs under train/runs/ are gitignored.
